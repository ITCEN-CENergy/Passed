# 채용공고 데이터 적재 및 임베딩 실행 가이드

## 1. 문서 목적

이 문서는 처음 프로젝트를 받은 사람이 다음 작업을 순서대로 수행할 수 있도록
설명한다.

1. PostgreSQL과 기준정보 준비
2. 채용공고 CSV를 `job_postings`에 저장
3. 공고 원문을 `job_posting_chunks`로 분리
4. 기술 스택·복리후생을 LLM으로 구조화
5. 추천 대상 청크를 OpenAI 임베딩으로 변환
6. 저장 결과와 실패 건수 확인

기존 FastAPI 서버와 데이터 적재·임베딩 작업자는 서로 독립적이다. FastAPI를
실행하지 않아도 아래 명령을 사용할 수 있다.

## 4. 환경설정

`passed-ai` 루트에서 예제 파일을 복사한다.

```powershell
Copy-Item .env.example .env
```

`.env`에서 최소한 다음 값을 실제 환경에 맞게 입력한다.

```dotenv
DATABASE_URL=postgresql://<사용자>:<비밀번호>@<호스트>:<포트>/<DB명>
OPENAI_API_KEY=<OpenAI API 키>

EMBEDDING_MODEL=openai/text-embedding-3-small
EMBEDDING_DIMENSION=1536
EMBEDDING_BATCH_SIZE=100
EMBEDDING_MAX_RETRIES=5
EMBEDDING_REQUEST_TIMEOUT_SECONDS=60
EMBEDDING_ONLY_MATCHING=true

CHUNK_MAX_TOKENS=400
CHUNK_OVERLAP_TOKENS=50

EXTRACTION_MODEL=gpt-4.1-mini
EXTRACTION_PROMPT_VERSION=v1
EXTRACTION_MAX_RETRIES=2
EXTRACT_WITH_LLM=true
```

주의:

- `.env`는 Git에 커밋하지 않는다.
- `.env.example`에는 실제 비밀번호나 API 키를 입력하지 않는다.
- API 키가 외부에 노출되면 즉시 폐기하고 새 키를 발급한다.
- `db.py`에 DB 비밀번호를 직접 작성하지 않는다.

## 5. DB와 기준정보 준비

### 5.1 pgvector와 파생 테이블

CSV 로더를 기본 옵션으로 실행하면 다음 SQL이 자동 실행된다.

```text
schema/00_extensions.sql
schema/01_job_posting_chunks.sql
schema/02_extraction_meta.sql
```

생성되는 주요 테이블:

- `job_posting_chunks`: 정규화된 공고 청크와 `vector(1536)`
- `job_posting_extraction_meta`: LLM 구조화 추출 캐시

DB 계정에 `CREATE EXTENSION` 권한이 없다면 관리자가 다음 SQL을 먼저 실행해야
한다.

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

### 5.2 산업·직무 기준정보

`job_postings.job_role_id`는 `job_roles.id`를 참조한다. 실제 산업·직무 기준
엑셀을 반영한 다음 SQL을 DB 클라이언트에서 실행한다.

```text
schema/seed_industries_job_roles_from_excel.sql
```

이 SQL은 다음 데이터를 준비한다.

- 산업 21개
- 직무 239개
- 직무 ID 1~239

직무 ID는 CSV의 `job_role_id`와 반드시 일치해야 한다.

### 5.3 개발용 임시 회사

현재 더미 CSV는 `company_id` 0~159를 사용한다. 로컬 개발 DB에 회사
기준정보가 없다면 다음 SQL을 실행한다.

```text
schema/dev_seed_companies_0_159.sql
```

이 데이터는 개발용이다. 운영 DB에서는 실제 회사 기준정보를 사용해야 한다.

### 5.4 기준정보 확인

```sql
SELECT COUNT(*), MIN(id), MAX(id)
FROM companies
WHERE id BETWEEN 0 AND 159;

SELECT COUNT(*), MIN(id), MAX(id)
FROM job_roles
WHERE id BETWEEN 1 AND 239;
```

개발용 더미 데이터 기준 정상 결과:

```text
companies: 160개, MIN=0, MAX=159
job_roles: 239개, MIN=1, MAX=239
```

## 6. 채용공고 CSV 적재

### 6.1 CSV 한 개 적재

```powershell
uv run python -m job_posting_pipeline.run_loader `
  data/job_postings_185_239_excel_safe_add_job_posting_id.csv
```

로더가 수행하는 작업:

1. UTF-8 또는 CP949 인코딩 감지
2. 필수값·날짜·숫자 검증
3. 회사·직무 외래키 사전 검증
4. `job_postings.id` 기준 UPSERT
5. 기술 스택·복리후생 LLM 구조화 추출
6. 원문 정규화와 청크 생성
7. `content_hash` 기반 변경 감지
8. 신규·변경 청크 저장 및 삭제된 청크 제거

### 6.2 CSV 여러 개 적재

여러 경로를 공백으로 구분한다.

```powershell
uv run python -m job_posting_pipeline.run_loader `
  data/job_postings_role_id_1_61_610rows.csv `
  data/job_postings_123_184_620rows_new_schema_add_job_posting_id.csv `
  data/job_postings_185_239_excel_safe_add_job_posting_id.csv
```

파일 경로에 공백이 있으면 반드시 따옴표로 감싼다.

```powershell
uv run python -m job_posting_pipeline.run_loader `
  "C:\데이터 폴더\job_postings.csv"
```

### 6.3 스키마 초기화 건너뛰기

파생 테이블이 이미 준비되어 있고 SQL 파일을 다시 적용하지 않을 때 사용한다.

```powershell
uv run python -m job_posting_pipeline.run_loader `
  --no-init `
  data/job_postings_185_239_excel_safe_add_job_posting_id.csv
```

### 6.4 정상 로그

```text
CSV 적재 완료 ... loaded=550 failed=0
공고 청크 처리 완료: total=550 success=550 failed=0
전체 적재 결과 loaded=550 failed=0 failures=0
```

다음 경고는 추출 결과 한 항목이 원문 근거 검사에서 폐기됐다는 의미이며 공고
전체 실패는 아니다.

```text
추출 폐기(tech_stack): ... evidence 가 원문에 없음
```

실제 실패는 `ERROR` 로그와 `공고 처리 실패` 로그를 확인한다.

## 7. 청크 적재 결과 확인

```sql
SELECT COUNT(*) AS posting_count
FROM job_postings
WHERE id BETWEEN 1841 AND 2390;

SELECT
    COUNT(*) AS chunk_count,
    COUNT(DISTINCT job_posting_id) AS posting_count,
    COUNT(*) FILTER (WHERE chunk_content = '') AS empty_chunk_count
FROM job_posting_chunks
WHERE job_posting_id BETWEEN 1841 AND 2390;

SELECT source_type, COUNT(*)
FROM job_posting_chunks
WHERE job_posting_id BETWEEN 1841 AND 2390
GROUP BY source_type
ORDER BY source_type;
```

`job_postings_185_239` 파일의 현재 검증 기준:

```text
job_postings: 550건
job_posting_chunks: 15,477건
청크가 생성된 공고: 550건
```

청크 개수는 LLM 추출 결과나 원문 변경에 따라 달라질 수 있으므로 반드시
15,477과 같아야 하는 것은 아니다. 공고 550건이 모두 청크를 가지고 있고
실패가 0건인지 확인하는 것이 중요하다.

## 8. 임베딩 실행

임베딩 작업자는 다음 조건의 청크만 처리한다.

```sql
embedding IS NULL
AND chunk_content <> ''
AND use_for_matching = true
```

### 8.1 한 배치 시험

먼저 기본 배치 100건만 처리한다.

```powershell
uv run python -m job_posting_pipeline.run_embedding --max-iterations 1
```

정상 로그:

```text
임베딩 배치 완료: iteration=1 success=100 failed=0 skipped=0
임베딩 작업 종료: ... remaining=<남은 건수>
```

### 8.2 전체 임베딩

한 배치가 성공한 뒤 전체 대기 청크를 처리한다.

```powershell
uv run python -m job_posting_pipeline.run_embedding
```

배치 크기를 일시적으로 변경할 수 있다.

```powershell
uv run python -m job_posting_pipeline.run_embedding --batch-size 50
```

`--batch-size` 허용 범위는 1~2048이다. 기본값 100을 권장한다.

### 8.3 재실행과 이어서 처리

작업이 중간에 종료되어도 이미 저장된 벡터는 다시 호출하지 않는다. 같은
명령을 다시 실행하면 `embedding IS NULL`인 청크부터 이어서 처리한다.

```powershell
uv run python -m job_posting_pipeline.run_embedding
```

재시도 한도를 초과한 배치는 같은 데이터를 무한 호출하지 않고 작업을
중단한다. 오류 원인을 해결한 뒤 명령을 다시 실행한다.

## 9. 임베딩 결과 확인

```sql
SELECT
    COUNT(*) FILTER (
        WHERE use_for_matching = true
          AND chunk_content <> ''
          AND embedding IS NULL
    ) AS pending,
    COUNT(*) FILTER (
        WHERE use_for_matching = true
          AND embedding IS NOT NULL
    ) AS completed,
    COUNT(*) FILTER (
        WHERE embedding IS NOT NULL
          AND vector_dims(embedding) <> 1536
    ) AS invalid_dimension
FROM job_posting_chunks
WHERE job_posting_id BETWEEN 1841 AND 2390;
```

전체 임베딩 완료 기준:

```text
pending=0
completed>0
invalid_dimension=0
```

추천 검색에서는 다음 조건을 항상 적용한다.

```sql
WHERE use_for_matching = true
  AND embedding IS NOT NULL
  AND chunk_content <> ''
```

## 11. 자주 발생하는 오류

### `companies.id 누락`

원인:

- CSV가 참조하는 회사 ID가 `companies`에 없음
- 다른 DB에 연결함

확인:

```sql
SELECT id FROM companies ORDER BY id;
```

로컬 개발 환경이면 `schema/dev_seed_companies_0_159.sql`을 실행한다.

### `job_roles.id 누락`

원인:

- 산업·직무 기준정보 미적재
- CSV의 `job_role_id`와 DB ID가 다름

해결:

```text
schema/seed_industries_job_roles_from_excel.sql
```

### `No such file or directory: schema/...`

원인:

- `job-posting` 디렉터리가 아닌 다른 위치에서 실행
- `schema` 디렉터리가 누락됨

해결:

- 작업 위치를 확인한다.
- 스키마가 DB에 이미 있으면 `--no-init`을 사용한다.

### `current transaction is aborted`

현재 코드는 행별 SAVEPOINT를 사용하므로 한 행 오류가 다음 행으로 전파되지
않는다. 이 오류가 반복되면 이전 버전 코드를 실행하고 있지 않은지 확인한다.

### OpenAI 호출 제한 또는 timeout

작업자는 호출 제한·timeout·연결·5xx 오류를 자동 재시도한다. 계속 실패하면
배치 크기를 줄이고 다시 실행한다.

```powershell
uv run python -m job_posting_pipeline.run_embedding --batch-size 20
```

### 임베딩 차원 불일치

다음 세 값이 모두 1536인지 확인한다.

```text
EMBEDDING_DIMENSION=1536
job_posting_chunks.embedding=vector(1536)
OpenAI API 요청 dimensions=1536
```

## 12. 재적재 안전성

- `job_postings`는 ID 기준 UPSERT이므로 같은 CSV를 다시 실행할 수 있다.
- 같은 `content_hash`의 청크는 기존 임베딩을 유지한다.
- 변경된 청크만 `embedding=NULL`로 초기화되어 재임베딩 대상이 된다.
- 원문에서 삭제된 청크는 DB에서 물리 삭제된다.
- 임베딩 저장 직전에 해시가 변경되면 오래된 API 결과를 저장하지 않는다.

## 13. 전체 실행 순서 요약

```text
1. uv sync
2. .env 작성
3. PostgreSQL/pgvector 준비
4. 산업·직무 기준정보 SQL 실행
5. 회사 기준정보 준비
6. run_loader로 CSV 적재 및 청크 생성
7. SQL로 공고·청크 건수 확인
8. run_embedding --max-iterations 1 시험
9. run_embedding 전체 실행
10. pending=0, invalid_dimension=0 확인
```
