# 이력서·자기소개서 스킬 후보 추출 프롬프트 명세

## 목적

임베딩이 완료된 사용자 문서 청크에서 `skills` 마스터에 매핑하기 전 후보를
구조화된 형태로 추출한다. 이 단계는 마스터 ID나 사용자 스킬을 저장하지 않는다.
숙련도 후보는 같은 LLM 호출에서 계산하되 다음 저장 단계의 입력으로만 전달한다.

## 출력 계약

```json
{
  "skills": [
    {
      "extracted_name": "Spring Boot",
      "category": "TECHNICAL_SKILL",
      "level": 2,
      "evidence": "Spring Boot로 결제 API를 개발"
    }
  ]
}
```

카테고리는 다음 네 종류만 허용한다.

- `TECHNICAL_SKILL`: 언어, 프레임워크, DB, 도구, 기술 개념
- `EXPERIENCE`: 직무, 산업, 프로젝트, 역할, 업무 수행 경험
- `BEHAVIORAL_TRAIT`: 행동으로 확인되는 협업, 소통, 리더십, 문제 해결
- `CERTIFICATION`: 공식 자격증, 면허, 공인 시험 자격

## 공통 규칙

1. 원문에 명시되거나 구체적인 행동으로 입증된 후보만 추출한다.
2. `evidence`는 원문에 존재하는 연속된 문구여야 한다.
3. `extracted_name`은 evidence가 입증하는 역량 하나를 짧게 원자화한다. 조사와 어미는
   정리할 수 있지만 여러 기술·행동을 묶거나 evidence에 없는 역량을 만들지 않는다.
4. 기술 대상과 서로 다른 행동을 분리한다. 예를 들어 REST API 설계·개발은 `REST API`,
   `API 설계`, `API 개발`로 나누고 AWS EC2·S3·RDS는 세 후보로 나눈다.
5. 희망, 포부, 지원 의지, 입사 후 계획만으로 현재 보유 역량을 만들지 않는다. 과거
   경험을 언급하더라도 문장의 주된 내용이 미래 의도라면 후보를 만들지 않는다.
6. 회사·학교·기관·교육 과정·행사·대회명은 제외한다. 실제 사용한 기술 제품·도구는 허용한다.
7. 자격증은 취득·보유 또는 공인 시험 성적이 명시된 경우만 추출한다. 필기 합격,
   준비 중, 취득 예정은 제외하고 복수 자격증은 각각 나눈다.
8. 이름과 카테고리가 같은 후보는 한 번만 반환한다.
9. `level`은 언급·학습·기본 사용=1, 실무 적용=2, 설계·최적화·리딩·정량 성과=3으로 정한다.
10. `CERTIFICATION`의 level은 보유=1만 허용하고 미보유=0은 후보 없음으로 표현한다.
11. 한 청크에서 최대 12개만 반환한다.
12. 근거가 없으면 빈 배열을 반환한다.

## 이력서 분기

- `EXPERIENCE`: 사용 기술, 수행 업무, 역할, 성과를 우선한다.
- `TRAINING`: 실제 학습·구현한 기술만 추출한다.
- `CERTIFICATION`: 자격증명은 `CERTIFICATION`으로만 해석하고 관련 기술 숙련도를
  추가 추론하지 않는다.
- `EDUCATION`: 전공·학업 경험과 명시 기술만 추출하고 학교 이름은 제외한다.
- 나머지 source type도 해당 항목에 명시된 사실만 사용한다.

## 자기소개서 분기

- `MOTIVATION`: 미래 포부는 제외하고 완료된 과거 경험만 사용한다.
- `PERSONALITY`: 성격 단어만으로 판단하지 않고 상황과 행동이 있는 특성만 추출한다.
- `EXPERIENCE`: 기술, 역할, 경험, 성과, 행동 특성을 균형 있게 추출한다.

## 검증

Pydantic Structured Outputs로 필드와 enum을 강제한 뒤에도 `evidence`가 실제
`chunk_content`의 부분 문자열인지 코드에서 다시 검사한다. `extracted_name`은 조사와
어미를 정리할 수 있으므로 부분 문자열 검사를 하지 않는다. 검사를 통과하지 못한 후보는
로그를 남기고 제외하며, 마스터 ID를 결정하는 책임은 다음 `map_to_skill` 단계에 둔다.
